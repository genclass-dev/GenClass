# Keystone Admin UI

Session brief for the adoption swarm (docs/adoption/swarm.md), 2026-11-03. Slug `keystone-admin-ui`, type hunt.

TARGET: Keystone Admin UI (keystonejs/keystone). TYPE: hunt (`docs/adoption/swarm.md` section 4.1). SLUG: keystone-admin-ui.

Why: The cheapest native setup on the list (one npm create, SQLite, port 3000) with an admin UI that is a dense CRUD surface: list views driven by URL search/filter/sort/page state, relationship selects with search-as-you-type, item forms that save whole items, and create drawers. Apollo keys queries by variables, so the likely unguarded paths are mutations, manual client.query calls and the relationship search (not inspected). Permissive policy: no CLA, DCO or AI rules, and discussions or PRs welcomed directly.

What to contribute: Hunt on an example app (examples/usecase-blog or examples/relationships) with the Admin UI; fix PR in packages/core/src/admin-ui (field or list component) with a test in the package's style; issue + hunt report.

Mechanism: PR to https://github.com/keystonejs/keystone (packages/core/src/admin-ui/... or packages/core/src/fields/types/relationship/views/...), optionally preceded by a GitHub Discussion as CONTRIBUTING.md suggests.

Stack: Node/TypeScript, Prisma (SQLite by default in starters and examples), GraphQL API; Admin UI in packages/core: Next.js 16, React 19, Apollo Client 4.1; pnpm 11.21 monorepo with 70+ examples (usecase-blog, usecase-todo, better-list-search, relationships) that run on SQLite.

Verifier's verdict (primary sources read 2026-11-03; re-check anything you rely on): Real, allowed, feasible and likely welcome: keystonejs/keystone is live (MIT, 9986 stars, pushed 2026-11-03), CONTRIBUTING.md welcomes issues and PRs with no CLA, DCO, AI policy or issue-first rule, the repo has no CLA workflow, and community bug-fix PRs (#10051, #10056) merged within 2 days with changelog credit. The Admin UI runs natively on SQLite from examples/usecase-blog (no login) in about an hour and is a fetch-driven Next.js/React/Apollo SPA with five race-prone surfaces whose files I read. The main caveat is yield: every data path I inspected is Apollo useQuery keyed by variables, the item save is diffed, guarded by useTransition and reconciled after refetch (PR #10052), and create is pending-guarded, so a "no race found" outcome is a real possibility; the session should treat it as a measured hunt, not a sure fix.
