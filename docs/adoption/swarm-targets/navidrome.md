# Navidrome

Session brief for the adoption swarm (docs/adoption/swarm.md), 2026-11-03. Slug `navidrome`, type hunt.

TARGET: Navidrome (navidrome/navidrome). TYPE: hunt (`docs/adoption/swarm.md` section 4.1). SLUG: navidrome.

Why: One `make dev` runs backend and UI together on SQLite, so the hunt is cheap. react-admin 3 list views refetch on every filter keystroke through a data provider that never cancels or sequences requests, so search-as-you-type, star/rating toggles, playlist editing and the play queue are natural explore targets. Clear contribution rules (issue first, DCO sign-off, conventional commits) and no anti-AI clause. 24.5k stars, music/media category that other finders are unlikely to take.

What to contribute: docs/adoption/hunts/navidrome.md, a patch to ui/src (data provider sequencing or the affected list/playlist component) with a vitest regression test next to ui/src/dataProvider/wrapperDataProvider.test.js, an issue draft and a PR draft (signed-off commits, conventional commit message) with AI-assistance disclosure.

Mechanism: Issue first via https://github.com/navidrome/navidrome/issues/new/choose, then a PR to navidrome/navidrome (master) from a branch named `<issue-title>/<issue-number>`; commits need `git commit --signoff` (DCO): https://github.com/navidrome/navidrome/blob/master/CONTRIBUTING.md

Stack: Backend: Go single binary, SQLite under DataFolder. Frontend: React 17 + react-admin 3.19 + redux + react-router 5; ui/src/dataProvider/httpClient.js wraps react-admin's fetchUtils.fetchJson (no AbortController), ui/vite.config.js dev server on 4533 with a proxy to the Go server.

Verifier's verdict (primary sources read 2026-11-03; re-check anything you rely on): Real, active (24,495 stars, pushed 2026-11-03, GPL-3.0, not archived), a documented native dev path on SQLite with no Docker (make setup / make get-music / make dev at http://localhost:4533/, admin auto-created by DevAutoCreateAdminPassword), an issue-plus-PR mechanism with DCO sign-off and no CLA, no AI/LLM policy anywhere (the maintainer runs Codex reviews on every PR), and the maintainer merged an outside fix for the very same hooks (useRating/useToggleLove, #6008 via #6009, "Nice catch, thanks!") in 13 days. At least three race-prone surfaces with no ordering guard exist in the code read today: rating (RatingField never disables while a request is in flight; setRating then getOne), playlist drag reorder (PUT then refetch of the same list signature, last delivery wins), and the love toggle driven from two views (list row and player bar, independent loading flags), all cross-cut by SSE-driven getMany refreshes. Costs: the cloud image's Node 22 fails the Makefile's Node 24 gate (install Node 24 first), the first build needs cgo and the race detector, and two of the finder's surfaces (search-as-you-type, form double submit) are largely guarded by react-admin 3.19, so the hunt should target rating, reorder and love, and measure false reports on search.
